## 1. 项目定位与目的

**一句话定位**：把投料管理标准化工作中的"日报监控 → 稽查判定 → 通报归因"全流程，从手工Excel筛查升级为**自动化数据校验Agent**——校验结论由确定性规则保证（可量化验收），异常洞察由大模型提供（深挖根因）。

**三层目的**（对应工作报告"固本·深挖·建制"思路）：

| 层 | 目的 | 对应痛点 |
|---|---|---|
| 固本 | 每日自动校验各厂预投/补投/余数/报废数据，替代手工Excel筛查，异常不漏查、指标反弹早发现 | 手工筛查效率低、稽查覆盖面有限 |
| 深挖 | 对命中的异常自动归因：是违规行为？流程定义不清？人员理解偏差？还是系统漏洞？并给出整改建议 | "只看到是什么，难挖为什么" |
| 建制 | 把校验规则沉淀为可执行插件+知识库，规则可迭代扩展；校验发现的异常规律反过来支撑系统硬管控需求提报 | "人防"升级"技防"需要规则标准化载体 |

## 2. 业务背景（源自《个人总结报告-郭志法.docx》）

- 岗位：投料模型管理标准化工程师（计划部），负责PCB生产预投/补投/余数入库/余数报废的日报监控、稽查通报、信息化需求提报
- 三大稽查项：① 违规投料（不按历史报废率/投料模型参数）② 违规报废（可用余数被报废）③ 违规入余数仓（在线有板且订单不够数时余数应留包装环节等并单出货）
- 已上线系统管控规则：在线有板禁入余数仓、有后批在线禁补投、同一订单当天禁重复补投
- 核心KPI：补投率（标杆3.93%）、余数报废占比、余数净入库占比，最终传导至不准交率（标杆1.50%）
- 工厂：珠海一厂、珠海二厂、江门一厂、江门二厂、金州厂
- 数据痛点：报表字段缺失/数据错误、各部门数据口径不一致、Excel手工处理效率低、稽查"只见是什么难挖为什么"

## 3. 成功标准（可量化验收）

1. **校验准确率（主指标）**：以历史稽查通报记录构造金标准数据集，违规项**召回率≥90%、误报率≤10%**；每次规则变更后跑全量回归
2. **效率**：一份日报从文件导入到异常报告生成 ≤5分钟（对比手工数小时）
3. **可追溯**：每次校验的工具调用、判定依据、模型推理全链路日志可回溯

## 4. 范围

**MVP（首期）**：
- 报表自动解析清洗（Excel/CSV，中文列名别名映射）
- 规则校验引擎（插件化结构，R1~R4先行）
- 异常报告输出（Excel + Markdown）
- 执行日志溯源（JSONL）
- LLM归因（基础版：归因分类 + 整改建议）

**二期**：
- 4类规则（预投/补投/余数入库/余数报废）完整插件化配置
- RAG知识库（规则文档需自行整理，本地向量库）
- LLM归因增强（接入RAG实时查询规则）
- 预投类规则（预大率区间、历史报废率对比，需历史数据与模型参数）
- Streamlit本地Web界面
- DeepSeek-Harness就绪后替换Agent编排层

## 5. 架构与组件

分层架构（确定性校验内核 + LLM归因，即"方案A"）：

```
┌────────────────────────────────────────────────────────┐
│ ① 入口层  CLI（main.py）：报表路径 + 工厂名 + 报表类型    │
├────────────────────────────────────────────────────────┤
│ ② 数据层  报表解析清洗：字段自动识别（中文列名别名映射）   │
│           + 数据质量检查（缺字段/类型错/空值 → 第0类异常）│
├────────────────────────────────────────────────────────┤
│ ③ 校验层  规则引擎：每条规则=一个插件（输入标准数据         │
│           →输出异常项）；MVP先行R1~R4硬规则               │
├────────────────────────────────────────────────────────┤
│ ④ 归因层  脱敏 → LLM（DeepSeek/Claude可切换）：            │
│           异常归因分类 + 整改建议（二期接RAG知识库）       │
├────────────────────────────────────────────────────────┤
│ ⑤ 输出层  异常报告（Excel+Markdown：位置/违反规则/归因/建议）│
│           + 执行日志（JSONL：每步输入输出、耗时、规则命中） │
└────────────────────────────────────────────────────────┘
```

目录结构：

```
PCB生产预投业务数据校验Agent/

│   ├── llm/                 # LLM封装：client（DeepSeek/Claude适配）

└── data/                    # 样例数据、金标准数据集
```

关键设计点：

1. **规则插件接口统一**：所有规则实现同一基类 `validate(df) -> list[Anomaly]`，Anomaly含{工厂、订单号、违规位置、违反规则编号、证据字段值}；二期插件化配置无需重构
2. **与DeepSeek-Harness解耦**：业务校验逻辑是纯Python库，Agent编排层为薄层；harness装好后只替换编排层，业务代码零改动
3. **数据质量问题也是异常**：报表字段缺失、数据错误作为第0类异常输出
4. **LLM双通道适配**：client统一OpenAI兼容接口，DeepSeek/Claude配置切换；归因失败时报告降级为"仅规则判定+证据"，不阻塞校验结果

## 6. 数据流（一次校验的完整时序）

```
用户: python main.py 补投日报.xlsx --工厂 珠海一厂 --类型 补投日报
  │
  ▼ [解析]   读sheet → 中文列名别名映射 → 类型转换/日期统一 → 标准化DataFrame
  ▼ [质检]   必填字段缺失 / 类型错误 / 重复行 → 第0类异常（数据质量问题）
  ▼ [校验]   规则引擎按注册顺序执行 R1→R2→R3→R4（每条规则独立插件）
  ▼ [汇总]   异常去重合并（同一订单命中多规则时合并展示，证据字段保留）
  ▼ [脱敏]   客户名/料号 → 代号（哈希映射，本地保留对照表）
  ▼ [归因]   LLM逐条生成：归因分类 + 整改建议
  ▼ [输出]   Excel异常报告 + Markdown摘要 + JSONL执行日志
```

## 7. 规则判定逻辑（MVP，**判定条件为可迭代变量**）

> 说明：以下判定条件基于当前业务理解拟定，**之后可能会更改**。为支持快速迭代：
> ① 每条规则的判定条件独立封装，改动只动一个文件；② 阈值类参数放 `config/settings.yaml` 不硬编码；③ 每条规则配有对应回归测试，条件修改时金标准预期同步更新；④ 规则编号（R1~Rn）作为异常报告的引用标识。

| 编号 | 规则 | 判定条件（当前版本） | 异常证据字段 |
|---|---|---|---|
| R1 | 违规入余数仓 | 有入库记录 且 在线数量>0 且 已产出总数<订单需求数 | 在线数、已产出数、需求数、入库时间 |
| R2 | 违规补投 | 有补投记录 且 该订单存在后批在线生产 | 后批批次号、在线数、补投时间 |
| R3 | 重复补投 | 同一(订单号, 日期)补投记录数 > 1 | 两次补投记录明细 |
| R4 | 违规报废 | 在线数量>0（仍有可用板）且 有报废记录 | 在线数、报废数量、报废时间 |

规则来源对照：R1/R2/R4 对应工作报告三大稽查项，R3 对应已上线系统管控规则。预投类规则（预大率区间、是否参考历史报废率）需历史数据与模型参数对比，放二期。

LLM归因输出结构（每条异常）：

```
{ 归因分类: 违规行为 / 流程不清 / 人员偏差 / 系统漏洞 / 数据错误 }
{ 归因说明: 结合该订单投料-在线-入库-报废数据链路的解读 }
{ 整改建议: 针对性的动作（如"提报系统管控需求"、"通报工厂"、"核实数据"）}
```

## 8. 错误处理策略

| 环节 | 失败情况 | 处理策略 |
|---|---|---|
| 报表解析 | 格式无法识别/表头字段缺失 | 明确报错"无法识别字段X"，列出与已支持报表的差异，不静默跳过 |
| 数据质检 | 缺字段/类型错/重复行 | 作为第0类异常进入报告，不阻塞校验 |
| 单条规则 | 规则执行报错 | 该规则标记失败并记入日志，其余规则继续执行（插件隔离性） |
| LLM归因 | API超时/限流/密钥错误 | 报告降级为"仅规则判定+证据"，不阻塞输出；日志记录重试次数 |
| 脱敏 | 脱敏失败 | fail-closed：脱敏不成功就不调用外部API（合规底线） |

## 9. 测试与验收

1. **规则单元测试**：每条规则一个测试文件，用构造的边界数据验证判定——R1的"刚好够数/差1块"、R2的"后批在线/后批已下线"、R3的"同天两次/跨天两次"等临界场景
2. **金标准回归测试（主验收）**：从历史稽查通报中挑各厂、各违规类型的真实记录 + 正常记录，去敏后构造金标准数据集。验收口径：召回率≥90%、误报率≤10%
3. **规则变更流程**：判定条件修改 → 同步更新该规则测试用例与金标准预期 → 跑全量回归通过才生效
4. **端到端烟雾测试**：一份样例报表跑通"解析→校验→归因→报告→日志"全链路
