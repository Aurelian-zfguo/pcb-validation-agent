# 关键决策记录

> 本文件收录项目 A（PCB生产预投业务数据校验Agent）开发及与项目 B（RAG知识库）联动过程中的关键架构决策，供新会话快速理解项目背景。

## 1. 架构：确定性规则校验 + LLM 归因（方案A）

- 背景：项目验收标准是"校验准确率"（召回率≥90%、误报率≤10%），要求校验结果可量化、可复现。
- 结论：规则判定用确定性 Python 代码（零幻觉、可单元测试），LLM 只负责异常归因和建议，避免幻觉影响校验结论。

## 2. 规则插件化（RulePlugin 基类）

- 背景：稽查判定条件会随业务规则调整（如"后批订单"的定义会变），不能写死。
- 结论：每条规则一个独立类文件，实现统一的 validate() 接口，改判定只动一个文件、可独立测试。

## 3. 字段别名映射 YAML 化

- 背景：各厂报表列名五花八门（"销售单号"/"单号"/"生产单号"），不能在代码里硬编码列名。
- 结论：用 field_mapping.yaml 配置"标准列名→别名列表"，解析器按映射统一重命名，新增列名只需加一行配置。

## 4. A 项目调 B 项目 HTTP 接口，而非直接读库（RAG 独立性）

- 背景：知识库（B 项目）是独立部署的检索服务，A 项目不希望硬依赖 B 的向量库和嵌入模型。
- 结论：A 通过 HTTP 调 B 的 /retrieve 接口，B 不可用/超时时静默降级为硬编码 Prompt，绝不影响校验主流程。

## 5. 多表关联分层匹配（精确 → 大行 → 未匹配）

- 背景：补投销售单号与订单 SO号-行 需要关联，但粒度不完全一致（销售单号带小数行号）。
- 结论：分三级匹配：精确匹配（完整销售单号 = SO号-行）→ 大行降级（销售单号去小数 = SO号-大行）→ 未匹配；左连接不丢主表行。

## 6. 历史报废率复刻 VBA（面积加权）

- 背景：报废率指标要与原有 VBA 模块（modMain.bas）的结果一致。
- 结论：用面积加权公式 Σ报废面积/(Σ报废面积+Σ入库面积) 而非算术平均；3批剔除最高1批、6批剔除最高2批。

## 7. 工厂名归一化（SUNTAK_ 前缀）

- 背景：真实数据的组织/工厂名带 "SUNTAK_" 前缀，与用户输入的工厂名不一致。
- 结论：统一用 normalize_factory 剥离前缀，匹配时两边都归一化。

## 8. 数据脱敏 fail-closed

- 背景：生产数据含客户名/料号，发外部 LLM API 有合规风险。
- 结论：客户/料号用哈希脱敏；脱敏不成功就不调外部 API（fail-closed）。

## 9. 预大率 >100% 强制数据错误（代码级）

- 背景：预大率 >100% 是确定性异常，不应依赖 AI 判断。
- 结论：在代码里强制把 category 覆盖为"数据错误"，不依赖 AI 输出，避免漏判。

## 10. 知识补充拼入输出，而非仅 Prompt

- 背景：知识拼入 Prompt 后，LLM 生成归因时不一定原样输出"【知识补充】"，报告里看不到制度条文。
- 结论：把检索到的知识直接追加到归因说明输出（保证报告可见），同时也拼入 Prompt 供 LLM 参考。

## 11. DeepSeek JSON 输出模式

- 背景：归因需要稳定的 JSON 结构输出，供程序解析。
- 结论：用 response_format=json_object 强制 JSON，输出约定为 {"results":[...]}；模型返回非法类别时钳制为"其他"。

## 12. GUI 通过 subprocess 调用 main.py

- 背景：加桌面 GUI 不能改 main.py 的核心逻辑。
- 结论：GUI 用 subprocess 运行 main.py，实时读 stdout 显示日志，完成后打开 output 目录；核心逻辑零改动。

## 13. B 项目：BGE 检索指令前缀用 query_encode_kwargs

- 背景：BGE 嵌入模型需要在查询侧加检索指令前缀，但前缀不应污染文档向量。
- 结论：查询侧前缀通过 query_encode_kwargs 配置（只在 embed_query 时自动加），文档侧走 encode_kwargs 不加前缀。

## 14. B 项目 Docker 容器化（A 调用无需改动）

- 背景：B 项目原先需手动启动 api.py 并加载 BGE/Rerank 模型，首次请求会因模型懒加载而超时降级。
- 结论：B 项目现已支持 docker compose up -d 一键启动 rag-api（:8000）+ rag-ui（:8501），模型改为启动时同步预加载；A 调用 /retrieve 无需改动，只需确保 B 容器运行、端口映射 localhost:8000。

## 15. B 项目 RAGAS 量化评估

- 背景：A 归因引用的知识片段此前无量化质量度量。
- 结论：B 项目用 RAGAS 对 15 条评估集评估 Faithfulness/AnswerRelevancy/ContextPrecision，修复意图路由 bug 后 Faithfulness 达 1.0，说明 A 引用的知识片段准确可靠。

## 16. 不做 LangGraph Checkpointer 断点续跑

- 背景：面试高频问题"任务中断怎么办"，考虑过用 LangGraph SqliteSaver 做断点续跑。
- 评估：
  1. A 项目是无环 DAG，重跑结果确定（异常判定确定性，LLM 归因虽随机但成本低）
  2. State 含 DataFrame / Tracer / Engine / LLM Client 等不可序列化对象
  3. 硬接需要把运行时句柄移出 State，是中等规模重构
- 结论：不做。Checkpointer 的价值在"避免重复副作用"（如循环 Agent、昂贵副作用），A 项目最贵步骤是 LLM 归因（几毛钱），重跑成本可接受。
- 未来方案：若要做，先把 tracer/engine/client 移到 runtime context，State 只留可序列化业务数据，再接 SqliteSaver + thread_id。
